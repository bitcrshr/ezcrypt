# Custody and formats

## Boundaries

Swift owns screens, public inventory, Keychain references, authentication, and
file sharing. Rust owns software CA generation, plaintext serialization,
encryption/decryption, signatures, and encrypted exports. The C boundary accepts
public JSON/ciphertext, a separate passphrase buffer, and a synchronous hardware
callback. It returns public metadata, a certificate, or encrypted export bytes.
There is no plaintext CA export operation in the app bridge.

A hardware CA is a permanent P-256 Secure Enclave signing key identified by a
per-CA application tag. Its public SEC1 point is passed into Rust. Rust frames the
certificate, calls the Apple signer for an ECDSA/SHA-256 DER signature, converts
that signature to SSH encoding, and verifies it against the CA public key before
returning the certificate. The bridge exposes certificate signing, not an
arbitrary-message signing command.

For software CAs, a separate per-CA P-256 Secure Enclave key performs ECDH. The
private CA itself is generated by Rust's `ssh-key` library. Hardware access uses
`privateKeyUsage` and `userPresence`, a fresh LAContext, and no retained unlock
session. Real device keys use WhenPasscodeSetThisDeviceOnly accessibility. Creation and key removal also explicitly evaluate device-owner
authentication. Authentication cancellation propagates as failure.

The Debug Simulator backend uses native software SecKey objects solely to test
the same ECDH/signature callback paths. It is compiled out for physical iOS devices, all Mac builds, and Release,
requires an explicit switch, has distinct Keychain tags and inventory location,
and is labeled on screen. It does not prove Secure Enclave behavior.

## Native Mac target

`ezcryptMac` compiles the same Swift source directory and the Rust core for
`aarch64-apple-darwin`. Only the navigation shell and small platform adapters are
Mac-specific. A single SwiftUI `Window` owns one shared inventory store; normal
Mac focus changes do not cover the window with the iOS app-switcher privacy overlay.
Sensitive key operations still authenticate through the shared cryptographic actor.

Mac SecItem create/load/delete operations explicitly select the data-protection
Keychain. The signed target requests only its own app-specific Keychain group,
App Sandbox, and user-selected read/write file access. There are no iCloud or
network entitlements. The separate local-test entitlement file omits Keychain
access and cannot qualify hardware operation support.

The local inventory schema is unchanged. Future public inventory synchronization
must separate public records from device-wrapped software-key envelopes; copying
this entire JSON file into iCloud is not the intended design. Cross-device signing
authorization is a later phase, with no protocol or trust changes in this target.

## Envelope v1

Each software CA record contains version, CA UUID, algorithm, fixed user/host
purpose, OpenSSH public key, device wrapping public key, ephemeral P-256 public
key, 32-byte random salt, 12-byte random nonce, and AES-256-GCM ciphertext/tag.

Rust generates an ephemeral P-256 key and agrees with the device public key.
HKDF-SHA-256 takes the raw 32-byte ECDH result, the salt, and the info prefix
`ezcrypt/software-ca/v1\0` followed by the authenticated metadata. Its 32-byte
output encrypts the binary OpenSSH private-key representation with AES-256-GCM.
AAD is the compact serde JSON tuple:

```
["ezcrypt-vault", version, id, algorithm, purpose, public_key,
 device_public_bytes, ephemeral_public_bytes]
```

Changing metadata, ciphertext, nonce, or salt fails authentication. Opening checks
an expected CA UUID and purpose, validates lengths/version, and checks that the
decrypted private key matches both the advertised algorithm and public key. There
is no device-key replacement or import path in v1.

On open, Apple's authenticated ECDH API returns a shared result that Swift copies
directly from CFData into Rust's zeroizing callback buffer. Swift never receives
the plaintext CA. That short-lived OS-owned CFData is outside Rust's allocator.

Rust scopes decrypted key objects and uses zeroizing plaintext/derived-key
buffers, with AES key-schedule zeroization enabled. It drops the shared secret after key derivation and plaintext serialized
bytes after parsing. Private-key types implement zeroization. The PGP message
builder borrows a reader over a zeroizing OpenSSH buffer instead of receiving an
owned plaintext `Bytes` copy. Rust never logs secrets or writes plaintext keys to
app files. Passphrases are separate from JSON; Rust/Swift byte copies are erased
and UI strings are cleared on completion/dismissal.

These measures do not guarantee erasure of compiler spills, registers, OS buffers,
Swift String storage, or all cryptographic-library internal scratch allocations.
A compromised process while a software key is decrypted can capture it. A software
export can sign independently of the phone's authentication thereafter.

## Certificates and issuance

Certificate framing follows OpenSSH PROTOCOL.certkeys and PROTOCOL.u2f. CA
signature algorithms are Ed25519 and ECDSA nistp256/384/521. Certificate subjects
also accept `sk-ssh-ed25519@openssh.com` and
`sk-ecdsa-sha2-nistp256@openssh.com`, preserving their application identifiers
and using their dedicated certificate type names. Resident and nonresident
keys share these public formats; no token discovery, enrollment, or hardware
attestation is performed. Private-key crypto and SSH
signature encoding use `ssh-key`, with the generated signature verified before
return. RSA and arbitrary critical options are rejected.

The stable ssh-key 0.6 certificate builder rejects unsigned timestamps above
`i64::MAX`; therefore ezcrypt frames certificates directly to encode OpenSSH's
`UINT64_MAX` forever sentinel. JSON uses `null`/absent end time for Forever, and
serials use decimal strings so all 64 bits survive bridge and UI round trips.
Finite validity uses Unix seconds and an exclusive end. Empty principals require
an explicit all-principals choice. For user certificates, the editor and review
warn that this is incompatible with `TrustedUserCAKeys`; per-account
`authorized_keys` CA trust without a principals restriction is required instead.
Source CIDRs reject nonzero host bits rather than silently broadening the network.

Duplicate identity includes CA and subject fingerprints, purpose, sorted/deduped
principals, critical options, and permissions. It excludes serial, key ID, and
validity. The UI warns on currently valid matches or intersecting validity
intervals and permits an explicit override. The check repeats at issuance.

The main-actor inventory serializes mutation. It reserves a serial on disk before
signing, so cancelled/failed attempts may leave gaps. Manual serials must be at
least the next available value. The maximum u64 serial exhausts that CA's local
serial allocator. This is local bookkeeping; restoring old storage or signing
with an exported key elsewhere is not globally coordinated.

After signing, the exact certificate is persisted before delivery. A disk-write
failure retains the signed result in memory and offers retry without signing
again. Recovery stays in the signing flow and opens the saved certificate for
delivery. If that flow is dismissed, a global recovery entry point offers the
same operation. A crash between hardware signing and the final disk write can lose an
undelivered certificate; its serial remains reserved. The app does not claim a
complete tamper-proof issuance audit.

## Storage and backups

Inventory is a versioned Codable JSON file with atomic replacement and complete
file-protection options on iOS. The Mac inventory is stored inside its app sandbox;
acceptance of those Foundation file options does not establish identical iOS
locked-device protection semantics. It contains public certificate history and encrypted CA
records. Corrupt or unknown-version stores fail closed rather than being reset.
Read errors offer an explicit retry and retry on foreground activation. Reloads
validate into a temporary value before replacing inventory, and a missing file
on retry is an error rather than permission to start an empty store. Certificate
status and filters update from a shared clock while the app is active.
Device-bound inventory is excluded from automatic backup. Portable exports are
explicit and contain only the CA key. Public history survives CA removal. Removal intent is persisted before deleting
the Keychain key; interrupted removals remain visible and can be retried.

Passphrase derivation and GPG recipient validation happen before the CA is
decrypted. The OpenSSH private block is encoded into a preallocated zeroizing
buffer and encrypted in place for passphrase exports. OpenPGP exports serialize
an armored plaintext OpenSSH key inside Rust, then encrypt it before returning.

Passphrase export: OpenSSH private-key format, bcrypt-PBKDF (64 rounds, random
16-byte salt), AES-256-CTR, minimum 12 characters. This is OpenSSH's interoperable
format, with its format/check-integer checks rather than an AEAD claim.
GPG export: OpenSSH private key in an AES-256 OpenPGP SEIPDv1 encrypted message,
using the recipient's valid encryption subkey. The encrypted message is
ASCII-armored as `BEGIN PGP MESSAGE` and saved with an `.asc` extension. Sharing
and the Copy encrypted backup button deliver the same armored ciphertext.
Temporary share files contain public certificates or ciphertext.

OpenPGP recipient parsing bounds input size, accepts one armor block, checks
definite-length packet framing before composed parsing, and rejects truncated
headers/bodies, secret/unrelated packets and supplied revocations. Unrelated
third-party user certifications are ignored after packet accounting; only
certifications cryptographically verified under the primary can supply policy.
User components still require a verified self-signature, subkeys require valid
bindings, and current key/signature expirations and encryption flags are checked.
Primary/subkey fingerprints are presented and the
primary fingerprint is checked again on export. This offline check cannot discover
revocations omitted from the input or establish who owns a fingerprint.
